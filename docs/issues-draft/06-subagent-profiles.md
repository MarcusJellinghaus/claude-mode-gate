# Subagent profiles

## Context

claude-mode-gate (plugin name `mode-gate`) is a Claude Code mod, written in TypeScript (strict), that gates Claude's tool calls. A fixed **baseline** allows reads, a few project writes and the check scripts. Named **profiles** add rules, each with `allow`, `ask` and `deny` lists in a subset of Claude Code's rule syntax. The user switches profiles with `/gate-on` and `/gate-off`, and inspects with `/gate-status`, `/gate-why`, `/gate-check` and `/gate-explain`. A **subagent** is a Claude run started by another Claude (the parent) through the Agent tool. **Headless runs** use `MODE_GATE_PROFILES`.

This is Draft 06 of 13 (plan: Draft 00). It makes delegation safe: a subagent gets only what its parent hands down.

## Design decisions this issue relies on

- A subagent gets the baseline plus the profiles its parent assigns at spawn. Its allow rules come from those only.
- **Who is a subagent.** Any call whose event carries an `agentId` (Draft 12) is a subagent call; the id is absent on the main loop. The id is also set for teammates and for the engine's own forks (compaction, memory), whose ids no list names. They get the same treatment: the baseline plus the main session's deny and ask lists, and an assignment only if a record binds to their id. **Consequence:** a fork or teammate that runs a Bash command outside the baseline is denied at decision step 1, in a headless run too, and its non-Bash calls fall under the main session's deny and ask lists. Draft 01 (assumption 21) records which forks call tools; the docs (Draft 13) state the consequence.
- **Restrictions are inherited, allows are not.** The `deny` and `ask` lists of the main session's active profiles also apply to every subagent (deny beats ask beats allow as usual). `allow` lists apply to a subagent only when assigned. Reason: a deny-only profile in the main session (for example a read-only profile) must not be escapable by launching a subagent. Authority still only narrows down the tree. A subagent's **effective set** is the baseline, its assigned profiles' rules and the main session's active profiles' deny and ask lists.
- **Assignment channel.** The parent assigns profiles in the prompt of its Agent tool call. The first line of the prompt is `mode-gate-profiles: name1, name2` (names separated by commas). An absent or empty marker means baseline only. The prompt is `e.prompt` on `tool.call` and `e.input.prompt` on `tool.check`, which Draft 12's normalisers put in `call.input.prompt`. One pure function, `parseAssignmentMarker(prompt)`, does the reading; the live wiring and `/gate-explain` (Draft 08) both use it, so they cannot drift. It splits the prompt on `\r?\n`, takes the first line, and for the form `mode-gate-profiles: a, b` returns the requested names: each trimmed, empty entries and duplicates dropped. An absent or empty marker returns an empty list.
- **Matching a launch to the new agent.** The key is the Agent call's `toolCallId` (`tool_use_id`). The mod keeps a pending assignment record keyed by that id and binds it to the subagent's agent id on the event that carries the new id (assumption 10 also asks which event or field that is, and whether it carries the `tool_use_id` or another value linking it to the call). Matching by arrival order or "the only pending record" is forbidden. If the launch cannot be linked to the new agent by a real identifier (no `toolCallId`, no id-bearing event, or an event without a linking value), the subagent gets the baseline only; this is the documented fallback. This prevents parallel spawns from swapping assignments.
- **Binding hook.** The binding is a `register.ts` registration (this draft owns it) on the event and matcher that Draft 01 row 10 names (candidates `agent.spawn`, `agent.offer`), using the result shape row 10 records. It must fire **before** the subagent's first gated call (`tool.call` or `tool.check` with the new agent id); Draft 01 row 10 also tests that ordering. If the ordering is not guaranteed, the fallback is baseline only for every subagent, written into `docs/design.md` before any code. The hook returns `next(e)` (it decides nothing), writes `$.state` only (it binds the pending record found under the event's linking value to the new agent id, intersecting with the caller's held set, and stores the result in `gate.assignments`), follows Draft 04's state-write rule, and has a fail-closed `.catch`: a throw leaves no binding, so the subagent is baseline-only, and the handler returns the pass-through result (never throws). It is a gating-style registration for `check:catch` (Draft 12 lists its event) and is added to the events lists of Draft 00 and `docs/design.md`.
- **Binding and revocation.** At bind time the assignment is intersected with the parent's currently held set, so a profile switched off in between is dropped. `/gate-off` and the session-end reset (Draft 04) also clear pending (not yet bound) records. `/gate-off` revocation uses the pure function `revoke(gate, names)` in `hooks/assignment.ts` (below), which `register.ts` applies after `commands.ts` returns the new `active`; `commands.ts` stays `{ active, message }` and imports nothing from `assignment.ts` at runtime.
- **Who writes the record.** It is written for any Agent call that is not denied, once, idempotently (keyed by `toolCallId`), only on the live decision path. The write lives in `register.ts`, outside `gate.ts`: after the shared path returns a non-deny verdict for an Agent call (`Agent` or the older name `Task`), `register.ts` writes the record using the full decision. `gate.ts` has no injection point for it, and `/gate-explain` (Draft 08) never runs that code, so a dry run cannot write it. A `tool.call` hook never sees an allow, so the write happens on whichever live hook first sees the call and returns a non-deny verdict; the key keeps a second write harmless. An Agent call that was denied or rejected as an invalid assignment writes nothing.
- **Timing of the write.** `next(e)` in `tool.call` runs the Agent tool, which is the whole subagent run. So in `tool.call` the record is written after the shared path returns a non-deny verdict and **before** `next(e)` is called; written after, it would not exist when the subagent's first event arrives, nothing would bind, and the subagent would silently get the baseline only. In `tool.check` the record is written after `next(e)` resolves (it runs no tool) and the path returns a non-deny verdict. A record written in `tool.call` for a call that Claude Code then denies stays pending and unbound; the reset and `/gate-off` clear it like any pending record.
- **Record fields and state types.** `gate.pending` is `Record<toolCallId, { requested: string[], caller: string }>` and `gate.assignments` is `Record<agentId, { parent: string, profiles: string[] }>` (this draft narrows Draft 04's loose types to these). The record holds the `toolCallId` (its key), the requested profile names and the calling agent's id (`main` for the main session). At bind time the mod intersects the request with the currently held set of that caller (the main session's active profiles, or the calling agent's assigned set), so it knows whose set to use. **Held set of a caller:** `main` holds `gate.active`; an agent id holds `gate.assignments[id].profiles`; an agent id with **no entry** in `gate.assignments` holds nothing (baseline only), so any marker naming a profile is denied by `checkAssignment`. The check never falls back to `gate.active` for a subagent.
- **Concurrent writes.** The pending-record write, the binding and `revoke` all follow Draft 04's state-write rule (re-read `gate` right before the set, no `await` between, change only the target field). Two Agent calls with different `toolCallId` values writing at the same time must both survive.
- The parent writes the advice to use only the assigned profiles into its own spawn prompt; the mod adds nothing to the prompt. That is advice. The mod's enforcement of the same list is what counts.
- The parent can assign only profiles it holds, so authority only narrows down the tree. The chain ends at the user. A parent's set is the main session's active profiles, or for a nested parent its own assigned set. A child's set is always a subset of its parent's, so nested agents can only narrow.
- **Invalid assignment.** If the marker names a profile the parent does not hold, or one that is not delegable (or unknown), the Agent call is denied. The deny is a guard-sourced result (`source` = `guard`), produced by the pure function `checkAssignment(requested, held, profiles)` in the new module `hooks/assignment.ts` (this issue owns it), where `held` is the caller's held set (`readonly string[]`, see Record fields) and `profiles` is `config.profiles`, a `Record<string, Profile>` (Draft 02). It returns the offending names (not held, non-delegable or unknown). `register.ts` wires it as a closure over `$.state` (the calling agent's held set from `gate.active` or `gate.assignments`, `gate.config`, the delegable flags). Draft 03's closed list of sources and Draft 12's guard context do not change. The message names the offending profiles and who decides: for a profile the parent does not hold, the parent; for a non-delegable profile, the user, via `/gate-on` in the main session.
- **No assignment record** (unknown agent id, wiped state, a spawn without a marker or without a binding): the subagent gets the baseline only (fail closed), still subject to the main session's deny and ask lists. This replaces Draft 12's placeholder, under which subagent calls used the session's active set.
- **Limit of enforcement.** Decision step 1 (the subagent-Bash deny) is Bash-only. A non-Bash call that no rule of the subagent's set matches keeps Claude Code's verdict, which is allow in a `bypassPermissions` agent. What is guaranteed: the allow rules of profiles that were not assigned never apply to a subagent, and the main session's deny and ask lists always do.
- **Revocation.** Switching a profile off in the main session removes it from the assignments of all descendants (children and grandchildren) and from pending records, through the pure `revoke(gate, names)` (below): it removes the names from every entry of `assignments` (grandchildren included, since the map is flat) and from the `requested` list of every pending record, and deletes a pending record whose list becomes empty through the removal. `register.ts` applies it after `commands.ts` returns the new `active`, with the names that left `active`. Assignments are cleared by the session-end reset (Draft 04: `session.end`, which is how `/clear` shows up); `session.start` clears nothing, because a hot reload re-fires it and the state must survive. Switching a profile on again does not bring delegated copies back.
- A denied subagent call returns a message with a **profile hint** (below). The subagent stops and reports. The parent decides; profiles marked non-delegable go to the user. There is no request tool.
- **Profile hint.** The function `profileHint(decision, call)` lives in `hooks/gate.ts` (Draft 12 owns it), because it needs `decide`; `gate.ts` puts its text in the denial `message`, and it is not added after the path returns. The live wiring and `/gate-explain` run the same function, so they show the same denial text. It uses Draft 12's per-profile probe (run `decide` with one candidate profile appended to the sets the injected effective-set function returns for the call) to name the profiles whose allow rules would match. This draft supplies the candidates through the injected function `availableProfiles(call)` (Draft 12): for a subagent call, the profiles the parent holds that the subagent lacks, plus the defined non-delegable profiles. "Available" means held by the parent and delegable. For a non-delegable profile that would match, the hint says to ask the user to run `/gate-on <name>`. Otherwise the message is generic. **For a subagent call this hint is the whole profile text of the deny message, also in a headless run**: it replaces Draft 12's headless list of all defined, switched-off profiles, which stays correct for main-session calls.
- Decision order step 1: a subagent calls Bash and no active allow rule matches this call: deny, with the redirect message (Draft 05). Then protected paths, then deny beats ask beats allow across the subagent's set. A deny from Claude Code passes through unchanged first.
- Security model row: "A subagent asks for more" is a confused-deputy risk, closed by "the parent decides, and non-delegable profiles go to the user".
- Later (not here): skills and agents declaring profiles in their definitions.

## Depends on unverified API facts

- Assumption 2 (partly verified): `agentId` is on both tool events and absent on the main loop. Whether `tool.check` still fires for a call that `tool.call` denied is open (it only affects log dedupe).
- Assumption 10 (partly verified): the Agent call input including the prompt is visible. Open: which event gives the new subagent's agent id together with the `tool_use_id` or another value linking it to the call, whether that event fires before the subagent's first gated call, and the binding hook's event name, matcher and return shape: all three come from the spike (Draft 01 row 10), not from memory.
- Assumption 11: hooks run for `bypassPermissions` agents. The three agents in `.claude/agents/` use that mode.
- Assumption 21: which engine forks and teammates carry an `agentId` and call tools.

**If assumption 10 or 11 fails, write the fallback into `docs/design.md` first, before writing code.** Fallbacks:

- Assumption 2 fails (no agent id on the events): the subagent-Bash deny is inert and every call counts as main-session. This is a documented limitation (README and PR).
- Assumption 10 fails (the launch cannot be linked to the new agent by a real identifier, or the binding event does not reliably fire before the subagent's first gated call): no assignment is possible, so subagents get the baseline only.
- Assumption 11 fails (hooks do not run for `bypassPermissions` agents): the mod cannot gate them. Stop and ask (see Working rules). Draft 10 then stops and asks at once too, without waiting for Drafts 06 and 09, and does not leave the three agents running ungated.

## Existing code

- `hooks/policy.ts`: pure; `decide` from Draft 03 takes `call.agentId`. `hooks/register.ts`: wiring; Draft 04 defines the `gate` state shape; this draft uses `gate.active` (the main session's active profiles), `gate.pending` (pending assignment records keyed by `toolCallId`) and `gate.assignments` (a map from agent id to its parent id and assigned profile names). Draft 12's shared path decides subagent calls with the session's active set; this draft replaces that with the subagent's effective set. It does so by supplying the function (call to effective set) that Draft 12's path takes by injection. That function is a closure over `$.state` in `register.ts` that wraps the pure helper `effectiveSet` (below); `/gate-explain --agent <id>` calls the helper directly with explicit lists and never touches `$.state`. Explain simulates a subagent call without assignment: the baseline plus the main session's deny and ask lists. Draft 12's shared path takes injected guard functions and the candidate-profile function `availableProfiles(call)`; the assignment check and the hint candidates plug in that way (`profileHint` itself lives in `gate.ts`). The record write does not: it is in `register.ts`, outside the path (before `next(e)` in `tool.call`, after it in `tool.check`; see Timing of the write). `/gate-explain` reuses `parseAssignmentMarker`, `checkAssignment` as a guard (the switched-on profiles are the held set) and the path's `profileHint`, and never writes records.
- `hooks/assignment.ts` (new, this issue): exactly four pure functions, `parseAssignmentMarker(prompt)`, `checkAssignment(requested, held, profiles)`, `effectiveSet({ baseline, profiles, active, assigned? })` and `revoke(gate, names)`. `profileHint` is not here (it needs `decide` and lives in `hooks/gate.ts`). `profiles` is `config.profiles` (`Record<string, Profile>`, Draft 02). `active` is the main session's active profile names and `assigned` the bound profile names of a subagent. `revoke(gate, names)` takes the plain `assignments` and `pending` data of `gate` and the revoked names, and returns the new `assignments` and `pending` (names removed from every assignment's profiles and from every pending `requested` list; a pending record that becomes empty through the removal is deleted); it touches nothing else. `effectiveSet` returns `RuleSet[]` (Draft 03): with `assigned` omitted the main-session set (baseline plus the active profiles); with `assigned` given, even empty, the subagent set: the baseline, the assigned profiles in full, and for every active profile that is not assigned a `RuleSet` named after it with an empty `allow` and its `ask` and `deny` lists (so `profile` in a decision reports the real name). It imports nothing at runtime (a type-only import of `RuleSet` is allowed), like `hooks/guards.ts` (Draft 05). It is added to the coverage include list in `vitest.config.ts` (95% thresholds), to the `mutate` list in `stryker.config.json` and to a dependency-cruiser purity rule (like `policy-is-pure`).
- `.claude/agents/commit-pusher.md`, `issue-approver.md`, `issue-updater.md`: copied from mcp-coder, run with `bypassPermissions`. Draft 10 replaces them: the supervisor skills launch plain subagents with `mode-gate-profiles: git-write` or `issues`.
- `CLAUDE.md` "Testing strategy": test through `decide`, negative test per security rule.

## Goal

Let a parent assign a subset of the profiles it holds to a subagent through its spawn prompt, enforced by agent id.

## Scope

- Add the pure `parseAssignmentMarker(prompt)` for the `mode-gate-profiles:` first line of an Agent call's prompt, used by the wiring and `/gate-explain`. Keep a pending record keyed by `toolCallId`; bind it to the new agent id on the id-bearing event.
- Add `hooks/assignment.ts` with the four pure functions (`parseAssignmentMarker`, `checkAssignment(requested, held, profiles)`, `effectiveSet`, `revoke(gate, names)`), `checkAssignment` wired in `register.ts` as a closure over `$.state`, and its three gates (coverage, mutation, purity).
- Add the binding hook registration in `register.ts` (event and matcher from Draft 01 row 10, returns `next(e)`, writes `$.state` only, fail-closed `.catch`) and add its event to `check:catch`'s list (Draft 12) and to the events lists in Draft 00 and `docs/design.md`.
- Deny an Agent call whose marker is invalid (a guard result from `checkAssignment`); write the record once, idempotently, in `register.ts` (outside `gate.ts`), only on the live path and only for an accepted call: in `tool.call` before `next(e)`, in `tool.check` after `next(e)` resolves.
- Enforce the effective set through the pure `effectiveSet` helper: baseline plus assigned profiles' rules plus the main session's deny and ask lists; the parent's allow rules are not inherited; no binding means the baseline plus those deny and ask lists. `register.ts` injects a closure over `$.state` that wraps it.
- The injected `availableProfiles(call)` closure (candidates for the denial hint; non-delegable flag honoured, field from Draft 02). The hint function `profileHint(decision, call)` itself is Draft 12's, in `gate.ts`.
- Bind-time intersection with the parent's current set; revocation cascades to all descendants through `revoke(gate, names)`, which `register.ts` applies after `commands.ts` returns the new `active`; clearing of bound and pending records on `/gate-off` and by the session-end reset.

## Out of scope / later

A request tool for subagents. Skill and agent declared profiles. Gating non-Bash calls beyond the subagent's rules.

## Acceptance criteria

- [ ] The marker is read from the first line of the Agent call's prompt only: `mode-gate-profiles: a, b` assigns `a` and `b`; the same text on a later line, an absent marker and an empty marker assign nothing (baseline only). The prompt comes from `call.input.prompt` for both `tool.call` and `tool.check` events.
- [ ] `parseAssignmentMarker(prompt)` is pure (exported from `hooks/assignment.ts`, imports nothing) and table-tested: `mode-gate-profiles: a, b` and `mode-gate-profiles:a ,  b` give `[a, b]`; CRLF line endings (`...: a, b\r\nrest`) give `[a, b]`; `a,,b` gives `[a, b]`; `a, b, a` gives `[a, b]`; an empty marker, no marker and the marker on a later line give `[]`. The live wiring and `/gate-explain` both call it.
- [ ] A subagent gets the baseline plus its assigned profiles' rules and the main session's active profiles' deny and ask lists; the allow rules of profiles that were not assigned never apply to it, even if the parent holds them.
- [ ] A call with any `agentId` (a teammate or an engine fork included) and no record is decided with the baseline plus the main session's deny and ask lists; its Bash call outside the baseline is denied (`subagent-bash`).
- [ ] The function from a call to its effective set is injected into the shared path of Draft 12; for a call with an agent id and no assignment (as in `/gate-explain --agent`) it returns the baseline plus the main session's deny and ask lists.
- [ ] `effectiveSet({ baseline, profiles, active, assigned? })` is pure (in `hooks/assignment.ts`, no `$`; `profiles` is the `Record<string, Profile>` of Draft 02), returns `RuleSet[]` and is table-tested: `assigned` omitted gives baseline plus all active profiles; `assigned: []` gives baseline plus one `RuleSet` per active profile, named after it, with an empty `allow` and its deny and ask lists; `assigned: ['a']` adds `a`'s allow, ask and deny (and no duplicate set for `a` if `a` is also active). A decision from an inherited deny reports that profile's name. The live closure over `$.state` only reads the lists and calls it; explain calls it with explicit lists and no `$.state`.
- [ ] A subagent without assignments is still subject to the main session's deny lists: with a deny-only profile (a read-only profile that denies `Edit`) active in the main session, the subagent's matching call is denied; an `ask` list of an active profile asks.
- [ ] Deny beats ask beats allow in the subagent's effective set: an assigned profile's allow does not override an inherited deny or ask.
- [ ] Two parallel spawns with different markers (`a` and `b`) each keep their own assignment: the first subagent's calls use `a`, the second's use `b`, whatever the order of the id-bearing events.
- [ ] A spawn with no `toolCallId`, or whose id-bearing event carries no linking value or cannot be matched to a pending record, gets the baseline only. With exactly one pending record and an id-bearing event without a linking value, the record is not bound (no matching by arrival order or "the only pending record").
- [ ] At bind time the assignment is intersected with the parent's currently held set: a profile the parent switched off after the spawn started is not bound.
- [ ] A record pending while `/gate-off <p>` (or a reset) runs never binds `p`; `/gate-off` and the reset leave no pending record for the revoked profile.
- [ ] Binding hook: `register.ts` registers it on the event and matcher recorded by Draft 01 row 10, exactly once (a repeat registration of the same pattern throws, mods-api-notes claim 9); the hook returns `next(e)`, writes `$.state` only (no file, no `$.fs`) and its registration carries a fail-closed `.catch` (wiring test: a throw inside the hook leaves `gate.assignments` unchanged, so the subagent is baseline-only, and the handler returns the pass-through result without throwing). `npm run check:catch` covers the registration (Draft 12's script lists the event; a fixture row proves a registration without `.catch` fails). If Draft 01 row 10 found no ordering guarantee before the subagent's first gated call, this criterion is replaced by the baseline-only fallback in `docs/design.md`.
- [ ] `revoke(gate, names)` is pure and table-tested: it removes the names from every entry of `assignments` (a child and a grandchild both lose `p`; a profile that is not named stays), removes them from every pending record's `requested` list, deletes a pending record whose list becomes empty through the removal (and keeps one with names left), leaves unrelated records untouched, and returns the input unchanged for an empty `names`. `register.ts` applies it after `commands.ts` returns the new `active`, with the names that left `active` (including every active name for `/gate-off all`), and `commands.ts` imports nothing from `assignment.ts` at runtime (wiring test).
- [ ] The assignment record is written once: repeating the same Agent call (same `toolCallId`) leaves one record. Concurrent writes survive: two Agent calls with different `toolCallId` values whose writes interleave (wiring test with two interleaved writers on a fake `$.state` that yields between steps) both leave their record, because each write re-reads `gate` right before the set (Draft 04's state-write rule); the same holds for a binding that interleaves with a record write. A dry run writes none, structurally: the write is in `register.ts` after the shared path returns, and `/gate-explain` only calls the path. An Agent call denied for an invalid assignment, or denied by any other rule, writes none.
- [ ] The record is written for any Agent call that is not denied, including one that Claude Code allows or asks about, by whichever live hook first sees the call and returns a non-deny verdict; a `tool.call` then `tool.check` pair for the same `toolCallId` leaves one record.
- [ ] Wiring test (fake `next` and fake `$.state`): in `tool.call` the record write happens before the `next(e)` call (a fake `next` that runs the "subagent" and reads the state sees the record); in `tool.check` the write happens after `next(e)` resolves. A `tool.call` deny writes nothing and never calls `next(e)`.
- [ ] The record stores the calling agent's id, or `main` for the main session. A grandchild's request is intersected at bind time with its parent's currently held set, not the main session's (test: parent holds `a`, main session switched `a` off, so the grandchild's `a` is dropped; with `main` as caller the main session's set is used).

- [ ] A marker naming a profile the parent does not hold denies the Agent call; the message names the profile and says the parent decides.
- [ ] A marker naming a non-delegable profile denies the Agent call; the message names it and says the user decides via `/gate-on` in the main session. An unknown name also denies the call and names it.

## Working rules

TDD, KISS, clean code, concise writing. Use the mcp-workspace MCP tools for file and git work; Bash only for `npm run ...` and git add, commit and push. Run `npm run check` before each commit. Commit and push after each major change.

**Stop and ask** (used in this issue) means: report to the owner in the session chat if an owner is attached, otherwise comment on the GitHub issue. List what is done and what is blocked, and leave the work uncommitted.
